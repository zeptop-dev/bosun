# Changelog

One entry per release tag, newest first, condensed from the commit subjects
between that tag and the previous one (`git log --format=%s <prev>..<tag>`).
Merge commits and formatting-only commits are left out. Binaries and
`SHA256SUMS` for every tag are on the GitHub Release; nodes update themselves
from there (Settings → Version and updates, or from Captain's node list).

- **v0.50.0** (2026-09-20) — **the speed limits heal themselves when another shaper wipes them.** Tools that pace the line for their own reasons — [tcpfit](https://github.com/Kylin010/tcpfit)'s `tcpfit-qdisc.service`, a hand-run tc script — start by deleting the root qdisc, which takes bosun's per-user classes with it; the desired limits have not changed, so the shaper's own no-op guard meant nothing would ever notice and the limits stayed gone. Every self-check (ten minutes, and shortly after each apply) now lists the classes and reinstalls them if any are missing, re-reading the root qdisc so it nests under whatever the other tool has just built. One `tc class show` per device when nothing is wrong. Running such a tool under a live bosun is now safe in either order.
  Also: the copy of the line's leaf qdisc that the catch-all class carries now takes **all** of its settings, not just `maxrate` — tcpfit tunes `limit 40960 flow_limit 8192` for high-BDP lines and unlimited traffic was falling back to fq's defaults. tc prints settings its own parsers will not read back (a packet count as `40960p`, a byte count as `3028b`), so those are handed back without the unit and a copy the kernel still refuses falls back to the bare qdisc rather than leaving the traffic with no leaf.
- **v0.49.7** (2026-09-20) — the doctor's "Panel contact" check no longer warns for the first minutes after a restart. Its first run happens before the first report of the new process has been acknowledged, so it always said "no report accepted yet" — and that snapshot is what the panel showed until the next doctor run, putting a warning on every node after every upgrade. A node that has been up for less than three report intervals with nothing accepted yet is reported as "just started"; after that it warns as before.
- **v0.49.6** (2026-09-20) — the line class gets its pacing back after a restart too: the qdisc bosun copies onto the catch-all *is* the copy of the line's, so clearing the limits reads it off the catch-all when the process that made it is gone.
- **v0.49.5** (2026-09-20) — two more ways the shaper left the kernel out of step, both found on a live node. A **first apply with no limits** was skipped — the empty set matches what a freshly started process has "already applied" — so classes installed before a restart stayed in the kernel for good, shaping users whose limits had since gone; the shaper now knows the difference between having applied nothing and not having run yet. And **clearing no longer deletes a root qdisc that is not bosun's**: it used to remove anything that was not someone else's HTB, which on a box whose init script sets an `fq` root for BBR pacing meant the pacing disappeared the first time the last limit did. Only bosun's own HTB is deleted now; a foreign HTB gives its classes back, as before; anything else is left where it is, and bosun never put classes under it anyway.
- **v0.49.4** (2026-09-20) — the shaper survives its own restart. `tc qdisc replace … root htb` fails outright on an HTB that is already there ("Change operation not supported by specified qdisc": HTB has no qdisc-level change operation), so every bosun restart with speed limits in place — an upgrade, most obviously — aborted the whole apply at the ifb device and left the kernel with the *previous* set of limits: users whose limit had gone kept their class, and a limit removed while the agent was down was never removed at all (seen on a live node right after the v0.49.3 upgrade). An HTB root that is bosun's own is now reused instead of replaced, any other root is deleted before the new one goes on, and the stale classes and their `fw` filters are found by reading what the kernel actually holds rather than what this process remembers installing — the only source that survives a restart. A foreign root qdisc under a handle other than `1:` is now followed properly as well (classes, filters and the catch-all all live in its major). The unit tests now drive a small `tc` stand-in that keeps state and enforces the kernel's rules, instead of replaying fixed output that agreed with anything.
- **v0.49.3** (2026-09-20) — the nesting from v0.49.2, finished: hanging the per-user classes under a foreign line class turns that class into an **inner** class, and HTB then drops everything the filters do not match into its direct queue — unshaped, past the line cap, which is the opposite of what nesting is for (measured on a real node: `direct_packets_stat` climbing while unlimited traffic ran). The shaper now also gives that traffic a leaf class of its own under the line class, with the line's rate and the pacing its leaf qdisc was doing (`fq maxrate …`), and a lowest-priority filter that sends everything unmatched there; the per-user filters still win. Clearing the limits removes the catch-all and gives the line class back the leaf qdisc it had.
- **v0.49.2** (2026-09-20) — per-user speed limits no longer throw away someone else's traffic shaping. The shaper used to `tc qdisc replace … root htb` on the egress interface and, when the last limit went, `tc qdisc del … root`: a line shaper installed by a VPS init script (HTB with an fq leaf, pacing the line under the provider's policer) disappeared the moment a user got a limit, silently, and never came back. bosun now reads the root qdisc first — an HTB that is not its own (its own is the one with `default 0`) is kept, and the per-user classes hang under the class that qdisc sends unclassified traffic to, so the line cap still applies above them; clearing removes only bosun's own classes and filters, and a user who loses their limit loses their class. Everything else (no qdisc, fq, fq_codel, mq, pfifo_fast, or bosun's own) is taken over as before. The status and the doctor report `nested_under`.
- **v0.49.1** (2026-09-20) — the firewall auto-open now also opens **80/tcp when the node gets a certificate itself over HTTP-01** (an `auto_cert` inbound that is not set to `dns`, or the decoy site). It only ever opened the ports the cores listen on, so with ufw active the first issuance still worked — from a machine whose firewall came later — and the renewal failed two months on, quietly. Also documented in the README: the firewall sync happens when bosun applies state, so enabling ufw under a running bosun needs a restart to take effect.
- **v0.49.0** (2026-09-19) — **forwards with several targets**: `spec.Forward` gains `targets` (further next hops with a weight), `balance` and `weight`, checked by the shared `Forward.ValidateTargets` on the panel and the node. `failover` (default) sends a new connection to the first hop whose probe is up, and a failed dial moves on to the next hop before the client has sent anything, marking that hop down at once; `roundrobin` spreads connections over the hops that are up by smooth weighted round-robin. Built-in relay: both modes, each hop probed concurrently with its own RTT and connection counters; realm: round-robin through `extra_remotes` and `balance` (no failover — realm does not retry); nft: refused. Reports carry per-hop status (`ForwardStatus.targets`); an older panel or agent ignores the new fields. The standalone panel edits the extra targets and shows each hop's health, and saving a forward there no longer drops `proxy_protocol`.
- **v0.48.1** (2026-09-19) — security toolchain release. Every Go binary bosun shipped was compiled with **Go 1.26.0**: setup-go v5 installed the `go` directive's version literally, so the release binaries and the sing-box builds missed the standard-library fixes of 1.26.1–1.26.8 (crypto/tls post-handshake message limits, net/http, html/template, encoding/asn1, crypto/x509 among them). `go.mod` now carries `toolchain go1.26.8`, which setup-go v6 installs, and the Docker build image is pinned to the same patch release. Cores: **sing-box 1.14.1-r2** (same upstream source rebuilt with Go 1.26.8) and **Xray 26.3.27-r1** — upstream's official 26.3.27 binary is Go 1.26.1, so a new `xray` workflow rebuilds the unmodified tag with upstream's own release flags; verified against a live node's config (`xray run -test`); **Hysteria 2.12.3** (upstream, already Go 1.26.8). A bare pinned upstream version (`cores.xray.version: "26.3.27"`, as the installer writes) now selects bosun's newest tested rebuild of that release, so existing nodes move to the rebuilt cores without a config change; a version with a suffix is still taken literally. CI: `govulncheck` gates every push and tag and runs weekly; Dependabot opens grouped weekly updates (Go minor, Node major and npm majors ignored).
- **v0.48.0** (2026-09-18) — **ShadowTLS v3** on Shadowsocks inbounds (`Inbound.ShadowTLS{handshake, strict_mode}`, sing-box only): the public port becomes a `shadowtls` listener that performs a real TLS handshake with a site you name and hands only authenticated clients to the Shadowsocks inbound, which moves to loopback. One password per user, derived from the UUID, so a client needs both credentials and revoking a user revokes both; `strict_mode` on by default. Subscriptions render it per client — mihomo and Stash as `plugin: shadow-tls`, sing-box as a carrier outbound the protocol outbound dials through, Surge and Loon as the flat `shadow-tls-*` keys, share links as `?plugin=shadow-tls;…` — always with the version written out, because every reader defaults to v2. The panel and the node both refuse a ShadowTLS inbound on any other protocol, on a non-sing-box core, or without a handshake target. Verified against a real sing-box: the rendered config passes `check` and starts.
- **v0.47.0** (2026-09-17) — the cores' own control APIs become root-only: sing-box's `v2ray_api` and xray's `api` are unauthenticated gRPC on loopback that can add users, edit inbounds and reset counters, and upstream offers no password for either, so the egress guard now drops every **non-root** connection to those ports — not just the core account's, so no other unprivileged process on the node can reach them either. The rule is installed even without `cores.user`, and the doctor's "Core isolation" line names the protected ports. Third layer behind the cores' own private-destination rejection and the egress drops.
